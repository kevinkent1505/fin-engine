# Database and Persistence

Fin Engine uses PostgreSQL as its durable source of truth. The current recommended hosted database is Neon.

## Why PostgreSQL

The data model is relational and historical:

- one source has many ingestion runs;
- one source has many stable source records;
- one source record has many time-series observations;
- future feature computation needs joins, grouping, percentiles and indexes.

PostgreSQL gives us a durable foundation without committing to heavier analytical infrastructure too early.

## Connection

The Python package reads:

```text
DATABASE_URL
```

Example Neon pooled URL:

```text
postgresql://USER:PASSWORD@ENDPOINT-pooler.REGION.aws.neon.tech/neondb?sslmode=require
```

`riil_analysis.database.config` converts normal PostgreSQL URLs to SQLAlchemy's psycopg 3 driver form internally.

Never commit a real database URL.

## Schema

Initial migration: `0001_initial_ingestion_schema.py`.

### `data_sources`

One row per logical ingestion source.

Important fields:

```text
source_key     primary key / registry ID
source_url     canonical source URL
created_at     first registration timestamp
```

Examples:

```text
kemendagri_njkb_2025
olx_authorized_crawl
mobil123_authorized_crawl
carmudi_authorized_crawl
djp_vehicle_auction_limits
```

### `ingestion_runs`

One row per successfully persisted ingestion run.

Important fields:

```text
id
source_key
started_at
completed_at
status
authorization_reference
requested_limit
request_delay_seconds
quality JSON
audit JSON
```

This table records operational provenance. It allows a developer to answer:

- when did this source last run?;
- what rate/limit was requested?;
- what permission reference was attached?;
- how many records were valid/invalid?;
- were duplicates or semantic failures detected?

### `vehicle_records`

Stable identity of one record inside one source.

Key uniqueness rule:

```text
(source_key, source_record_id)
```

For a marketplace, `source_record_id` should normally be the marketplace listing ID.

For an official reference source, it is the source-specific row/record identity.

Important fields:

```text
source_key
source_record_id
source_url
make
model
variant
type_name
year
region
category
first_seen_at
last_seen_at
latest_metadata
```

`vehicle_records` does **not** currently represent a universal physical-vehicle identity.

### `vehicle_observations`

Append-only observations attached to a `vehicle_record` and an `ingestion_run`.

Important fields:

```text
vehicle_record_id
ingestion_run_id
observed_at
price
price_kind
currency
njkb
weight_factor
dp_pkb
dp_pkb_expected
dp_pkb_difference
dp_pkb_check
metadata_json
```

Uniqueness inside one run:

```text
(ingestion_run_id, vehicle_record_id)
```

This prevents the same stable source record from being inserted twice within a single persisted run.

## Why observations are append-only

Suppose one listing is seen repeatedly:

```text
2026-10-01  Rp218,000,000
2026-10-05  Rp214,000,000
2026-10-10  Rp209,000,000
```

Fin Engine retains all three observations.

Do not update the previous `vehicle_observations` row to the latest price. History is a product asset.

Possible future features:

```text
price_change_absolute
price_change_pct
days_observed
days_since_first_seen
number_of_price_changes
listing_persistence
```

## Migrations

Alembic owns schema changes.

Apply all migrations:

```bash
cd apps/analysis
uv run alembic upgrade head
```

Show current revision:

```bash
uv run alembic current
```

Show history:

```bash
uv run alembic history
```

Create a new migration after changing SQLAlchemy models:

```bash
uv run alembic revision --autogenerate -m "describe change"
```

Review every autogenerated migration before committing it.

Then test both upgrade and downgrade where practical:

```bash
uv run alembic upgrade head
uv run alembic downgrade -1
uv run alembic upgrade head
```

For production-like databases, do not casually downgrade destructive migrations.

## Development rule for schema changes

A schema change should normally include all of the following in the same change set:

1. SQLAlchemy model changes;
2. Alembic migration;
3. persistence/query changes;
4. tests;
5. documentation updates if semantics changed.

Do not rely on `Base.metadata.create_all()` for production migration management. Tests may use it for temporary databases, but deployed databases should use Alembic.

## Persistence behavior

`persist_ingestion()` currently:

1. ensures the source exists;
2. creates an `ingestion_run`;
3. finds or creates each stable `vehicle_record`;
4. updates the record's latest canonical fields and `last_seen_at`;
5. inserts a new append-only `vehicle_observation`;
6. commits the transaction.

A repeated marketplace crawl should therefore produce:

```text
vehicle_records        same stable listing identity
vehicle_observations   +1 historical observation per run
```

## Example persistence command

```bash
cd apps/analysis

uv run fin-engine-data ingest \
  --source mobil123_authorized_crawl \
  --authorization-ref "permission-reference" \
  --request-delay-seconds 2 \
  --limit 5 \
  --persist-db
```

CSV output is optional:

```bash
uv run fin-engine-data ingest \
  --source mobil123_authorized_crawl \
  --authorization-ref "permission-reference" \
  --limit 5 \
  --persist-db \
  --output ../../data/generated/mobil123-small.csv
```

## Useful SQL

Recent runs:

```sql
SELECT
  id,
  source_key,
  started_at,
  completed_at,
  status,
  quality
FROM ingestion_runs
ORDER BY started_at DESC
LIMIT 20;
```

Record and observation counts:

```sql
SELECT COUNT(*) FROM vehicle_records;
SELECT COUNT(*) FROM vehicle_observations;
```

Counts by signal type:

```sql
SELECT price_kind, COUNT(*)
FROM vehicle_observations
GROUP BY price_kind
ORDER BY COUNT(*) DESC;
```

Price history for one listing/source record:

```sql
SELECT
  vr.source_key,
  vr.source_record_id,
  vo.observed_at,
  vo.price,
  vo.currency
FROM vehicle_records vr
JOIN vehicle_observations vo
  ON vo.vehicle_record_id = vr.id
WHERE vr.source_key = 'olx_authorized_crawl'
  AND vr.source_record_id = 'LISTING_ID'
ORDER BY vo.observed_at;
```

Latest observations by make/model:

```sql
SELECT
  vr.make,
  vr.model,
  vr.year,
  vr.region,
  vo.price,
  vo.price_kind,
  vo.observed_at
FROM vehicle_records vr
JOIN vehicle_observations vo
  ON vo.vehicle_record_id = vr.id
WHERE vr.make = 'Toyota'
  AND vr.model = 'Avanza'
ORDER BY vo.observed_at DESC
LIMIT 100;
```

## Indexing

Current indexes support:

- source/run chronology;
- make/model/year/region lookup;
- observations by signal type/time;
- observation history by source record.

Do not add indexes speculatively. Add them when query plans or production workloads show a need.

## Neon guidance

For short-lived jobs, use the pooled connection string.

Keep the Neon region close to Cloud Run when possible to reduce latency and cross-region networking.

Store `DATABASE_URL` in a secret manager for cloud deployments. Do not bake credentials into images or command arguments.

## Future database evolution

Likely additions:

```text
canonical_vehicle_entities     cross-source entity resolution
source_raw_payloads            metadata/pointer to object storage
feature_snapshots              derived analytical features
valuation_runs                 reproducible valuation outputs
```

Potential PostgreSQL extensions such as PostGIS should be introduced only when geographic analysis requires them.

High-volume analytical databases such as ClickHouse are intentionally deferred until PostgreSQL becomes a demonstrated bottleneck.
